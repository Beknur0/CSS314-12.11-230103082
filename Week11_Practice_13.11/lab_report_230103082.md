## Phase 3: Empirical Roofline and Cache-Blocked GEMM

### Part 3A: Empirical ceilings

Both tests used six worker processes.

| Measurement | Median, ms | IQR, ms | Result |
|---|---:|---:|---:|
| Copy two 64 MB shared-memory buffers | 8.94 | 0.80 | 14.32 GB/s |
| Scalar arithmetic, 60 million FLOPs per worker | 1266.76 | 230.83 | 0.2842 GFLOP/s |

The estimated ridge point is:

I* = 0.2842 / 14.32 ≈ **0.0198 FLOP/byte**.

The copy bandwidth counts both reading and writing, and includes
pool dispatch overhead. The arithmetic result is a ceiling for this
Python test, not the hardware peak. Each `a * b + c` is counted as
two FLOPs; Python does not guarantee a hardware FMA instruction.
The arithmetic IQR was substantial, indicating variability between
runs.

### Part 3B: GEMM variants and tile sweep

Matrix size: N = 256; worker processes: 6. Timings include
zeroing the output matrix and dispatching tasks to the process pool.

| Variant | Median, ms | IQR, ms | GFLOP/s |

| BS | Median, ms | IQR, ms | GFLOP/s | Tile footprint, bytes | Estimated FLOP/byte | Max error |

| 8 | 1134.22 | 106.62 | 0.0296 | 1536 | 0.67 | 0 |
| 16 | 967.95 | 69.48 | 0.0347 | 6144 | 1.33 | 0 |

| 64 | 930.56 | 29.94 | 0.0361 | 98304 | 5.33 | 0 |
| 96 | 1093.63 | 236.07 | 0.0307 | 221184 | 8.00 | 0 |
| 128 | 982.84 | 131.06 | 0.0341 | 393216 | 10.67 | 0 |

All blocked results matched the reordered result within the required
tolerance of 10⁻⁹. The smallest median was obtained at BS = 64:
the naive median was approximately 1.33 times as long.

The estimated footprint for BS = 64 is 96 KiB. It exceeds the
48 KiB L1d cache per core but is smaller than the approximately
1.25 MiB L2 cache per core, assuming the reported aggregate L2
capacity is divided equally among the six cores. This comparison is
approximate: the row partitions and edge tiles are not all full-sized.

The tiled intensity estimates, from 0.67 to 10.67 FLOP/byte, exceed
the empirical ridge point of approximately 0.0198 FLOP/byte. Under
this simplified roofline model, the tiled variants therefore lie on
the compute-ceiling side. The measured throughputs of all three
variants (0.0271–0.0361 GFLOP/s) are below the Python arithmetic
ceiling of 0.2842 GFLOP/s. Operational intensities for the naive and
reordered variants were not measured, so their positions relative to
the ridge cannot be established from these results alone.

These ceilings are only rough comparisons: Python interpreter and
loop overhead, process dispatch, memory access patterns and
measurement variability are not fully represented by the roofline
model. The performance differences cannot be attributed to cache
effects alone.

## Phase 4: Skewed Workloads and Dynamic Scheduling

The experiment used N = 8,000 items and six worker processes.
Each item performed K(i) = 1 + floor((i/40)²) iterations.
Each configuration was run once; wall time includes process startup.

| Strategy | Chunk size | Wall time, s | Imbalance λ |
|---|---:|---:|---:|
| Block static | — | 16.333 | 2.508 |
| Cyclic static | — | 6.865 | 1.017 |
| Dynamic queue | 1 | 6.601 | 1.002 |
| Dynamic queue | 8 | 6.832 | 1.008 |
| Dynamic queue | 64 | 6.678 | 1.053 |
| Dynamic queue | 512 | 7.699 | 1.315 |

All configurations produced the same displayed checksum,
11623.220144.

Block static had the greatest imbalance because the cost increases
with the item index: workers assigned later contiguous ranges received
more work. Cyclic scheduling distributed heavy items more evenly.

The best measured dynamic chunk size was C* = 1, with a wall time
of 6.601 s and λ = 1.002. Small chunks improve balance but require
more synchronized counter accesses. Larger chunks reduce counter
accesses but can leave a heavy tail: C = 512 had λ = 1.315 and
took 7.699 s. Because each configuration was run only once, the
small differences between C = 1, 8 and 64 should not be treated as
conclusive without repeated measurements.
